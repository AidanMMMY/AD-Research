# 邮箱自助注册链路设计（2026-10-25）

> 目标：访客无需管理员介入，凭邮箱完成自助注册 → 邮箱验证 → 自主设置用户名密码 → 直接使用。
> 设计原则：**简易友好、不拒人门外**；每一步出错都有明确出路；复用既有安全资产（密码策略、Redis 限流、双令牌）；可用一个环境变量整体关闭。
> 状态：设计稿，待用户拍板决策点后实施。

## 1. 用户旅程（3 步进系统）

```
注册页（一屏三字段）        验证页（OTP/链接）           完成
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ 邮箱              │   │ 输入 6 位验证码    │   │ 自动登录          │
│ 用户名（实时查重） │ → │ （或点邮件里链接） │ → │ 进 Dashboard     │
│ 密码（策略提示）   │   │ 60s 重发倒计时    │   │ 欢迎横幅+引导     │
└──────────────────┘   └──────────────────┘   └──────────────────┘
```

- **第 1 屏只有一个动作**：邮箱 + 用户名 + 密码，全部实时校验（防抖 400ms），密码框下方是改密页同款策略提示（12–64 字符、至少 1 字母 1 数字，Unicode code point 计数）。
- **第 2 屏验证**：6 格 OTP 输入（自动进格/退格、粘贴自动分列、Enter 提交）；同时邮件里带一个**魔法链接按钮**，点链接等效验证（移动端一键完成，无需手输）。
- **第 3 步零操作**：验证通过即签发 access/refresh 双令牌，自动登录直达 Dashboard。

### 每一步的「不拒之门外」设计

| 用户遇到 | 系统行为 |
|---|---|
| 验证码输错 | 前 4 次只红框提示「还差一位？」，第 5 次作废并主动问「给你发一封新的？」 |
| 验证码过期（10 分钟） | 同上，一键重发（60 秒冷却） |
| 邮件没收到 | 重发按钮 + 「换个邮箱重新注册」链接（已填用户名带回，不用重填） |
| 用户名被占用 | 输入时实时提示，并给 3 个可用建议（如 `aidan_2026`） |
| 邮箱已注册 | **不报错不泄漏**：照样回 201，给该邮箱发「你已有账号，直接登录」邮件（防枚举 + 不让人尴尬） |
| 注册到一半关页面 | 账号保留 24 小时，回来重发验证码即可续上；24h 未验证自动清理 |

## 2. 关键决策（含推荐）

| 决策点 | 推荐 | 理由 |
|---|---|---|
| 验证码 vs 验证链接 | **两者都发，一封邮件** | 链接是主按钮（最少操作），验证码是正文兜底（链接被邮件客户端拦截/换设备时可用） |
| 登录主键 | **保持用户名登录，邮箱是身份/恢复渠道** | 不动现有登录链路、native 契约零改动；未来找回密码靠邮箱 |
| 注册后立即可用 | **是**，`role=user` 与现有自助用户同权 | 「不拒之门外」；平台无付费分级，无需审批 |
| 验证方式存储 | 验证码 **sha256 哈希落库**，魔法链接用**短时效 JWT**（15min，`purpose=register_verify`） | 码不落明文；链接零额外存储 |
| 未验证用户 | 注册即建 user 行（含 bcrypt 哈希），`email_verified_at=NULL` 阻止登录 | 密码哈希不离开 users 表，无需中间暂存 |
| 总开关 | `AUTH_REGISTRATION_ENABLED`（默认 false） | 上线节奏可控，出问题秒关 |

## 3. 后端设计

### 3.1 数据模型与迁移

- `users` 新增：`email VARCHAR(255) UNIQUE NULL`（存量用户 NULL，不强制补绑）、`email_verified_at DATETIME NULL`
- 新表 `email_verifications`：`id, user_id FK, code_hash, expires_at(10min), attempts(默认0), consumed_at NULL, created_at`
  - 重发 = 作废旧码 + 生成新码；同邮箱 60s 冷却、3 封/小时
- Alembic：`b3c5d7e9f1a2` → 新单一 head；存量数据零迁移

### 3.2 端点（挂 app/api/v1/auth.py）

| 端点 | 行为 |
|---|---|
| `GET /auth/check-username` | 用户名可用性查询（供前端实时查重） |
| `POST /auth/register` | 校验（邮箱格式/用户名规则/密码策略）→ 建 user（未验证态）→ 发验证邮件 → 201。用户名占用返回字段级错误；邮箱已注册伪装成功（防枚举） |
| `POST /auth/verify-registration` | 验证码核对（sha256 常数时间比较、≤5 次尝试、单次有效）→ 置 `email_verified_at` → **签发双令牌返回**（自动登录） |
| `POST /auth/resend-verification` | 60s 冷却 + 3/h 限流，作废旧码发新码 → 202 |
| `GET /auth/verify-link?token=` | 魔法链接：JWT 校验（15min、purpose）→ 等效验证 → 302 到前端验证成功页 |

- 登录链路只加一条门：`email_verified_at IS NULL` 且注册开关开启 → 403 + 明确文案「账号未完成邮箱验证」+ 指引重发（区别于密码错误，让用户知道下一步做什么）
- 限流复用现有 Redis rate_limit 工具：register per-IP 5/h + per-email 3/h；verify per-email 10/h
- 审计：`registration_created / registration_verified / registration_blocked` 三类事件入既有日志；**任何日志不含验证码明文**

### 3.3 邮件发送

- 新增 `app/services/transactional_email.py`：薄封装，复用全局 SMTP 配置（host/port/user/password/from，SSL 465 语义与 notification_service 一致）+ `md_to_email_html` 的样式基调
- 模板 `app/templates/email/verify_registration.html`：中英双语、大号验证码、主按钮=魔法链接、纯文本 alternative、无追踪像素
- 发送策略：同步发送 + 失败重试 1 次（注册量小，不引入队列复杂度）；发送失败不阻塞 201 响应（前端有重发出口）

### 3.4 清理

- 24h 未验证账号：挂到既有 APScheduler 夜间任务（如每日 04:00）批量删除，日志记录条数

## 4. 前端设计（web/）

### 4.1 结构

- 新路由 `/register`、`/register/verify`；登录页底部「创建账号 →」链接，卡片滑动切换（与登录页同款背景/晨光主题延续）
- 不新增全局 store：局部 `useState` + React Query mutation；注册成功即写令牌 → 复用现有 `me` 查询与 `RequireAuth`，零改造

### 4.2 组件与 UI 巧思（克制的新意）

| 组件 | 交互细节 |
|---|---|
| `InlineField` | 防抖 400ms 实时校验；邮箱/用户名错误文案人话（「这个名字已经被占用了，试试 aidan_2026？」） |
| `PasswordPolicyHints` | 复用改密页逻辑 + **双色强度条**（长度 × 字符类，达标变绿不再恐吓） |
| `OtpInput` | 6 格：输入自动进格、退格回退、整段粘贴自动分列、错误时格子抖动（shake）一次、成功时绿色涟漪扩散后自动跳转 |
| `ResendButton` | 60 秒**环形倒计时**小圈包住重发按钮，冷却结束轻微弹跳提示可点 |
| 成功页 | 自动登录的 1.2 秒里展示「邮箱已验证 ✓」小动画，随后无感进 Dashboard；新用户首访横幅（可关闭）带 3 个引导链接 |

- 全程键盘可达（Enter 一路到底）；错误提示 `aria-live`；暗色模式全量走既有 token（不硬编码颜色，遵守 UI 一致性口诀）
- 移动端优先适配：单列、输入框 16px+ 防 iOS 缩放、OTP 格子 44px 触控区

### 4.3 原生端（native / 旧 iOS）

- **本期不动**：注册入口只在 Web；native 登录契约零变化（未验证用户在 native 登录会收到 403 文案 + 引导到 Web 完成验证，Phase 2 再考虑 native 内嵌注册）

## 5. 测试与实施拆解

- **红测先行**（先复现失败再实现）：未验证登录被拒 / 验证码过期、错误 5 次、重发冷却、防枚举（已注册邮箱回 201）、限流、密码策略复用、魔法链接过期与 purpose 校验 —— 约 15 个后端用例；前端 vitest 覆盖 OTP 交互与表单校验
- **P0（1–2 天）**：迁移 + 后端四端点 + 事务邮件封装 + Web 注册/验证页主链路 + 开关
- **P1**：魔法链接打磨、欢迎横幅、24h 清理任务、`check-username` 建议
- **P2（可选）**：native 注册入口、存量用户设置页补绑邮箱、找回密码（复用同一套验证码基建）

## 6. 待你拍板的决策点

1. **SMTP 现状确认**：目前全局 SMTP 指向你的 163 邮箱（授权码是否已配置生效？）。事务邮件量小可先用；到达率敏感后再换专用发信服务（域名+SPF/DKIM）
2. **开放注册的节奏**：建议先 `AUTH_REGISTRATION_ENABLED=false` 部署，你自己走一遍全链路，确认邮件样式与到达率后再开
3. **注册即用**是否接受（推荐是）；若想收紧，可加「新用户 24h 内只读」之类的灰度，但会复杂化
4. **用户名规则**：现有 `String(50)`，建议注册限定 `^[a-zA-Z0-9_]{3,30}$`（防奇怪字符与冒充），可接受？
